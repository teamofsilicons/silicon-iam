Refresh, introspection, revocation and logout are modelled as operation values: you build one, read its idempotency key, persist that key with your input, and only then send it. The shape exists because of one contract fact.

Refresh tokens rotate on every use, and reuse revokes the family. Presenting a consumed refresh token revokes every session in the 900-day family — every device — and raises a security audit event. A careless retry does not fail; it signs your user out everywhere.

Refresh

let operation = client.oauth().refresh(OAuthRefreshToken::new(stored)?);
let operation_key = operation.idempotency_key();

// Persist `operation_key` alongside the old token BEFORE sending.
let replacement = operation.send().await?;
let _was_replayed = replacement.operation().idempotency_replayed();

// Atomically replace the stored refresh token with the new one.
Ok(replacement.into_parts())

Two rules, both load-bearing:

  • One refresh at a time per token family. Two concurrent workers, two browser tabs, or a retry racing its own first attempt will each present the same token. Serialise it — a database row lock, a distributed lease, whatever your deployment already has.
  • Replace the old token atomically on success. A crash between receiving the replacement and storing it leaves you holding a token that no longer works, with no way back.

idempotency_replayed() reports whether the server returned a stored result rather than performing a fresh rotation. It is the signal that your recovery path worked.

Recovering an uncertain refresh

If the process restarts mid-refresh, rebuild the same operation rather than starting a new one: 

let operation = client
    .oauth()
    .refresh_with_idempotency_key(OAuthRefreshToken::new(stored)?, saved_key);
let replacement = operation.send().await?;

Same key, same input, same result — the server replays its stored response. Issuing a new key for the same mutation is what triggers the family revocation, so never "recover" that way.

Introspection

Tokens are opaque; there is nothing to verify locally. When an Application needs to know whether a token is good right now — after a revocation, or a membership change — it asks: 

let introspection = client
    .oauth()
    .introspect(&access_token)
    .send()
    .await?;

if let ActiveToken::Active(active) = introspection.token() {
    let _actor = active.actor();
}

The response reflects current revocation and organization-membership state. A webhook is a notification channel, never an authorization one: do not substitute a delivered event for an online check on a request that matters.

Revocation and global logout

Both follow the same operation pattern as refresh.

// Revoke one token this Application issued.
client.oauth().revoke(token).send().await?;

// End the user's IAM session across every configured Application.
client.oauth().global_logout(&access_token).send().await?;

Global logout is only available when the Application is the token's own audience, and it revokes every IAM and Application authority bound to that parent session — not just yours. Reach for it when the user asked to sign out of everything, not merely out of your product.

The operation pattern, in one place

  1. Build the operation. Nothing has been sent.
  2. Read idempotency_key() and persist it with the input.
  3. send().await.
  4. On success, commit the result and the key's retirement together.
  5. On a transport or protocol error, keep both and rebuild the same operation later.
  6. On an authoritative terminal error, retire the key.

Every mutating call in this SDK works this way, which means one recovery routine covers all of them. The general rules are in Errors and recovery.
