On-behalf-of lets your Application call another one in the same organization, without either holding the other's credentials. The SDK signs the exchange and binds the resulting proof to one exact downstream request.

Discover, then exchange

let catalog = client.discover_obo_endpoints("billing_app").await?;
let endpoint = catalog
    .endpoint("create_invoice")
    .ok_or("OBO endpoint not registered")?;

let body = br#"{"amount":1200}"#;

let exchange = client
    .exchange_obo(endpoint, &subject_token)
    .metadata(json!({"reason": "checkout"}))?
    .request_bytes(Method::POST, body)?;

let _operation_key = exchange.idempotency_key();
let proof = exchange.send().await?;

Discovery returns the audience's registered endpoints and the metadata each one requires. The SDK signs the registered path from the catalog rather than a path you type, so a mismatch is impossible.

The bytes never go to IAM. request_bytes hashes the body and sends only the digest. The payload — a file, an invoice, whatever it is — travels directly from your Application to the audience.

What the proof is bound to

The proof commits to the method, the registered path, the body digest and the idempotency key. It cannot be lifted and replayed against a different call, even by the Application that legitimately obtained it.

It is valid for one request or sixty seconds, whichever comes first. Exchange immediately before dispatching, not in advance.

Consuming a proof

On the audience side, verify against the request you actually received:

let result = client
    .verify_obo(proof)
    .request_bytes(Method::POST, "/v1/invoices", body)?
    .send()
    .await?;

// Only now execute. `result` carries the bound actor, endpoint and metadata.
Verification is single-use and must never be retried. It accepts no idempotency key, no successful response is ever stored, and every attempt after the proof is consumed returns 409. If your HTTP layer retries automatically, exempt this call — a retry after a successful verification is indistinguishable from a replay attack and will be refused as one.

When the SDK cannot tell whether a verification succeeded it returns Error::AmbiguousOboVerification. The proof may already be consumed. Fail the request; do not retry.

Recovering an uncertain exchange

The exchange is idempotent, so it can be rebuilt after a restart with exchange_obo_with_idempotency_key — but only after rediscovering the endpoint and restoring the same subject token, metadata, method and body digest. Any difference produces a different canonical request and a 409 idempotency_conflict rather than a replay.

Note the asymmetry: the exchange is recoverable, the verification is not. That is deliberate. Minting a proof twice is harmless because a proof is single-use anyway; consuming one twice is exactly the thing single-use exists to prevent.

How the proof reaches the audience

It does not travel by a header the SDK invents. The backend contract does not define how the issuer places a proof on the downstream request, so the SDK deliberately leaves that to the two Applications to agree — a header, a field, a wrapper envelope, whatever fits their protocol.

Inventing one here would look like a standard without being one, and the first Application to assume it was would be wrong.

Failure modes

ConditionMeaningDo
403The two Applications are not in one organization Nothing. This is not retryable and never will be.
409The proof was already consumed Do not retry. Mint a new proof for a new request.
410 proof_expiredMore than 60 seconds elapsed Exchange again, and look at why the gap was that long.
422Metadata does not satisfy the declared schema Re-read the catalog; the audience may have changed it.

The language-independent description of all of this is in the contract's OBO section.
