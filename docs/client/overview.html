silicon-iam is the official Rust client for integrating an Application with Silicon IAM. It keeps wire paths, authentication headers, signatures, response validation and retry policy inside the crate, and exposes only the inputs an Application actually owns.

What it covers

AreaWhat the SDK does for you
Connection The unversioned compatibility handshake, then every later call pinned to the agreed API major.
Login The short-lived-token exchange, token refresh, introspection, revocation, and Application-triggered global logout.
Delegation Same-organization, request-bound on-behalf-of proof exchange and single-use verification, including the HMAC over method, path and body digest.
Webhooks Exact-byte signature verification, secret-version transitions, and the complete Silicon event-type catalog.

What it deliberately does not cover

Carbon identity and organization administration are not exposed. Those endpoints require a direct IAM bearer belonging to a human, not an Application's client credentials. Putting them behind an Application client would invite exactly the confusion the contract's separate transports exist to prevent.

Signup, login, invitations, tags, trust and governance are console operations. If you are building an interface for them you want an IAM bearer and the HTTP contract directly, not this crate.

The design rule

Everything a caller can get wrong and would not notice is inside the crate. Everything a caller genuinely owns is a parameter.

A signature computed over re-serialised JSON still produces a hex string. A refresh retried after an ambiguous response still returns a token — right up until it revokes the user's entire 900-day family. These are the failures that pass a smoke test and surface weeks later, so the SDK does not offer the option of getting them wrong.

Operational guarantees

  • Secrets are redacted from Debug, and response buffers carrying secrets are zeroized.
  • Token and proof responses are rejected unless they carry the documented no-store cache headers.
  • Redirects are disabled, response sizes are bounded, and production transport is HTTPS-only. Literal loopback HTTP can be enabled explicitly for local integration tests.
  • Safe, idempotent calls retry only within a small bounded policy. A server Retry-After longer than that policy is surfaced to the caller rather than silently shortened.
  • API errors retain the request ID, retry metadata and rate-limit metadata, and never include credentials.

Where to go next

Connecting covers installation and the handshake. After that the sections match the order an integration is actually built: sign users in, manage their tokens, delegate between applications, and receive directory events. Before shipping, use a testing environment to prove the entire integration without production identities.
