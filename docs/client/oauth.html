Authorization Code with PKCE, in three steps. The SDK generates and holds the PKCE verifier and the CSRF state; the Application supplies only its callback URI, the scopes it wants, and somewhere to keep one opaque string between the two halves of the flow.

Step one — build the redirect

let options = AuthorizationOptions::new(
    "https://app.example.com/auth/callback",
    ["profile", "obo.issue"],
)?.for_organization("engineering")?;

let attempt = client.oauth().begin_authorization(options)?;
let redirect = attempt.authorization_url().to_string();
let continuation = client.oauth().seal_authorization_attempt(attempt)?;

// Persist `continuation`, then redirect the user agent to `redirect`.

The callback URI must match one currently registered and active for the Application, exactly. for_organization is optional and narrows the session to one organization.

The continuation

A PKCE flow has to carry the verifier and the state across a browser redirect. The SDK hands you one opaque string instead of two secrets to manage:

PropertyWhy
Encrypted and authenticated The verifier never leaves the process in plaintext.
Application-bound A continuation from one Application cannot be restored by another.
API-major-bound It cannot survive a version change that altered the flow's meaning.
Redacted from Debug It cannot reach a log line by accident.
Expires in 10 minutes Matches the authorization request's own lifetime.

Store it wherever you would keep a pending-login record: a session row, a signed cookie, a short-lived cache entry. It is inert without the Application's own credentials.

Step two — handle the callback

let continuation = AuthorizationContinuation::from_encoded(stored)?;
let attempt = client.oauth().restore_authorization_attempt(&continuation)?;

match attempt.parse_callback(callback_url)? {
    AuthorizationCallback::Granted(grant) => {
        let exchange = client.oauth().exchange_authorization_code(grant);
        let _operation_key = exchange.idempotency_key();
        let tokens = exchange.send().await?;
        Ok(Some(tokens.into_parts()))
    }
    AuthorizationCallback::Denied(denial) => {
        let _code = denial.code();
        Ok(None)
    }
    _ => Ok(None),
}

Pass the exact callback URL your framework received, query string and all. parse_callback checks the state against the restored attempt; handing it a reconstructed or normalised URL defeats that check.

A denial's description and error URI are untrusted input. They arrive in the query string and are attacker-influenceable. Branch on denial.code(); never render the description to a user or write it into a log without escaping it.

Step three — delete the continuation, carefully

This is the part that is easy to get subtly wrong.

OutcomeDo
Tokens received and durably committed Delete the continuation in the same transaction that stores the tokens.
Authoritative terminal API error Delete it. The grant is dead and cannot be retried.
Transport error, timeout, or process crash Keep it.
The user denied access Delete it immediately.

Keeping the continuation through an uncertain outcome is what makes the flow recoverable. Another instance can restore the same attempt, re-parse the same callback, and reproduce the same idempotency key — so the exchange replays server-side instead of failing, and the user never sees a login that half-succeeded.

exchange.idempotency_key() is available before send precisely so it can be persisted alongside the continuation. See Errors and recovery for the general pattern.

Handling the tokens

into_parts yields the access token, the refresh token, and the granted scopes. Both tokens redact themselves from Debug and require an explicit expose_secret to read.

Store them only in a secret store. An access token lives 30 minutes; a refresh family lives 900 days and rotates on every use — which is the subject of Managing tokens, and the single easiest thing to get wrong in an integration.
